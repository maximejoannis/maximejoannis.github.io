Présentation du projet

French Companies Explorer est un projet personnel d’automatisation des tests d’une application web permettant de rechercher, consulter, comparer, sauvegarder et exporter des informations sur les entreprises françaises.

J’ai conçu ce projet pour démontrer une démarche QA complète allant de l’analyse fonctionnelle à l’industrialisation des tests, avec une traçabilité inspirée des pratiques ISTQB. Le projet est publié en version stable v1.0.0.

Objectifs et portée

L’objectif était de concevoir un framework Playwright maintenable capable de vérifier les parcours critiques de l’application tout en maîtrisant les risques liés à une API publique et à des données évolutives.

Le périmètre couvre :

  • la recherche par nom, SIREN et SIRET ;
  • les filtres, tris et la pagination ;
  • les fiches entreprises et établissements ;
  • les favoris et leur persistance ;
  • la comparaison d’entreprises ;
  • l’historique et les recherches sauvegardées ;
  • les exports JSON et CSV ;
  • la gestion des erreurs et données partielles ;
  • l’accessibilité au clavier et la sémantique ARIA ;
  • la régression visuelle.

La suite comprend 39 tests techniques, produisant 110 exécutions automatisées sur les différents projets Playwright.

Méthodologie

Analyse fonctionnelle

J’ai commencé par réaliser une analyse boîte noire de l’application afin de produire une cartographie fonctionnelle, les User Stories et critères d’acceptation, les scénarios Gherkin, une stratégie fondée sur les risques, un plan de test, les cas de test et une matrice de traçabilité.

User Story → Critère d’acceptation → Cas de test → Preuve automatisée

Stratégie d’automatisation

J’ai adopté une stratégie complémentaire plutôt qu’une suite composée uniquement de tests E2E :

  • tests API ciblés sur le service réel ;
  • parcours E2E critiques avec l’application et l’API réelle ;
  • tests fonctionnels avec réponses HTTP simulées pour les erreurs, cas limites et données déterministes ;
  • tests d’accessibilité avec Axe et navigation clavier ;
  • tests de régression visuelle sous Chromium.

Les tests mockés exécutent le frontend réel dans un navigateur, mais remplacent les réponses de l’API publique avec page.route() et route.fulfill(). Ils vérifient le comportement fonctionnel de l’interface, et non les règles métier internes du backend.

Architecture Playwright

  • un Page Object Model par domaine fonctionnel ;
  • des fixtures Playwright typées pour injecter les Page Objects ;
  • des locators privilégiant les rôles et noms accessibles ;
  • des data-testid stables pour les entités métier dynamiques ;
  • des jeux de données centralisés ;
  • des tags et annotations pour la sélection et la traçabilité ;
  • une fixture automatique transformant les métadonnées Playwright en labels Allure.

Défis rencontrés

Dépendance à une API publique

Les données réelles évoluaient et certaines exécutions pouvaient devenir instables ou lentes selon le réseau et le navigateur. J’ai conservé quelques parcours contre l’API réelle et déplacé les variantes, erreurs et cas limites vers des tests fonctionnels avec API simulée. Cette séparation a réduit le caractère aléatoire de la suite sans masquer les risques d’intégration.

Reproduction des scénarios négatifs

Il était difficile de provoquer volontairement une erreur 503, une page suivante en échec ou certaines données partielles avec l’API publique. L’interception réseau Playwright m’a permis de construire des réponses contrôlées et reproductibles, puis de vérifier les messages, la récupération et l’absence de doublons dans l’interface.

Stabilisation multi-navigateurs

Certaines exécutions variaient selon le temps de réponse de l’API et le nombre de workers. J’ai réduit les dépendances aux données réelles, privilégié les assertions auto-réessayées, supprimé les attentes arbitraires et fixé deux workers par défaut.

Références visuelles Windows et Linux

Les snapshots générés sous Windows n’étaient pas compatibles avec le rendu Linux de GitHub Actions. J’ai généré et versionné les références visuelles dans un Codespace Linux afin d’aligner l’environnement de création avec celui de la CI.

Accessibilité et testabilité

Certains contrôles ne possédaient pas de nom accessible suffisamment explicite et le compteur de résultats n’était pas annoncé aux technologies d’assistance. Les anomalies ont été corrigées dans l’application, puis les tests ont été conservés sans assouplissement de leurs assertions.

Sécurité des exports CSV

Un scénario de test a mis en évidence un risque d’injection de formule pour les cellules commençant par =, +, - ou @. La correction applicative a neutralisé ces valeurs. Le test CT-032 est passé au vert sans modification de son résultat attendu.

Compatibilité de l’outillage

TypeScript 7 n’était pas compatible avec la plage de versions supportée par typescript-eslint. J’ai utilisé TypeScript 6 afin de conserver une chaîne ESLint officiellement compatible, sans recourir à --force ou --legacy-peer-deps.

Enseignements

  1. Un test vert ne signifie pas que tout le périmètre fonctionnel est couvert.
  2. La couverture doit être mesurée depuis les exigences, et non depuis le nombre de fichiers de test.
  3. Les tests mockés sont complémentaires des tests API et E2E, mais ne les remplacent pas.
  4. Les données déterministes réduisent fortement les faux échecs.
  5. Les snapshots doivent être produits dans le même environnement que la CI.
  6. Les locators accessibles améliorent à la fois la robustesse des tests et la qualité de l’application.
  7. Un test peut légitimement révéler un besoin de correction applicative pour améliorer la testabilité.
  8. Une traçabilité utile doit relier les exigences aux preuves réellement exécutées.
  9. Les rapports doivent rester accessibles aux profils techniques comme fonctionnels.
  10. Le nombre de tests, le nombre d’exécutions et la couverture fonctionnelle sont trois indicateurs distincts.
